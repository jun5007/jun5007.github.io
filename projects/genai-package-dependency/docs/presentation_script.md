# Presentation Script

## Page 1

1쪽. 표지 
안녕하세요. 저희는 생성형 AI(에이아이) Python(파이썬) 패키지 간 의존성 관계를 주제로 
발표하겠습니다. 이번 발표에서는 Python(파이썬) 패키지들이 서로 어떤 패키지에 의존하
는지 네트워크로 분석하고, 생성형 AI(에이아이) 생태계의 구조가 어떻게 변화했는지 살
펴보겠습니다. 
2쪽. 목차 
발표 순서는 연구 배경, 연구 질문, 데이터 수집과 전처리, 변수 설명, 분석 방법, EDA(이
디에이), 분석 결과, 결론 순서로 진행하겠습니다. 
3쪽. 연구 배경 
최근 생성형 AI(에이아이) 관련 Python(파이썬) 패키지는 매우 빠르게 증가하고 있습니
다. 하지만 단순히 유명하거나 많이 언급되는 패키지만 봐서는 실제 생태계의 핵심 구조
를 알기 어렵습니다. 그래서 저희는 패키지 간 의존성 관계를 통해 실제로 어떤 패키지
가 중심적인 역할을 하는지, 그리고 어떤 패키지들이 구조적으로 비슷한지 확인하고자 
했습니다. 
4쪽. 연구 질문 
연구 질문은 네 가지입니다. 첫째, 유명한 AI(에이아이) 패키지와 실제로 많이 의존되는 
패키지는 같은가. 둘째, 시간 흐름에 따라 어떤 기반 패키지가 중요해졌는가. 셋째, 과거
에는 중심적이었지만 현재 상대적 중심성이 낮아진 패키지는 무엇인가. 넷째, 같은 계열 
안에서 구조적으로 유사한 대체/경쟁 후보를 찾을 수 있는가입니다. 
5쪽. 데이터 수집 
데이터는 PyPI(파이피아이) 공식 메타데이터 API(에이피아이)에서 수집했습니다. 분석 대
상은 생성형 AI(에이아이) 관련 Python(파이썬) 패키지 50개이며, LLM API(엘엘엠 에이피
아이), Framework/Agent(프레임워크/에이전트), Model Runtime(모델 런타임), 
App/Service(앱/서비스), RAG/Vector DB(랙/벡터 디비)의 5개 계열로 분류했습니다. 기간
은 2022년 말부터 2026년 현재까지로 설정했고, 패키지의 버전 정보와 의존성 정보, 그
리고 일부 대표 패키지의 코드 구조 정보도 함께 활용했습니다. 
6쪽. 데이터 전처리 
전처리는 크게 세 단계로 진행했습니다. 먼저 패키지 명칭을 통일하고, 개발 버전이나 후
보 버전이 아닌 안정 버전만 사용했습니다. 그 다음 requires_dist(리콰이어스 디스트) 문
자열을 파싱해서 source(소스)에서 target(타깃)으로 향하는 의존성 엣지로 변환했습니다. 
마지막으로 필수 실행 의존성과 선택 기능 의존성을 구분했습니다.

7쪽. 결측치 처리 
시계열 분석에서는 결측치 처리가 중요했습니다. 예를 들어 어떤 패키지가 2024년에 처
음 출시되었다면, 2022년에 데이터가 없다고 삭제하면 안 됩니다. 삭제하면 나중에 등장
하는 패키지 자체가 분석에서 사라지기 때문입니다. 그래서 본 연구에서는 출시 전 상태
로 플래그를 남겨, 시간이 지나며 생태계가 확장되는 흐름을 보존했습니다. 
8쪽. 기본 변수 
기본 변수는 패키지명, 계열, 분석 시점, 버전, 의존성의 출발 패키지와 도착 패키지 등입
니다. 여기서 핵심은 source_package_norm(소스 패키지 노름)과 target_package_norm(타
깃 패키지 노름)인데, source(소스)는 의존하는 패키지, target(타깃)은 의존 대상이 되는 
패키지를 의미합니다. 
9쪽. 모델 변수 
모델 변수에서는 네트워크 분석 지표를 사용했습니다. in-degree(인 디그리)는 다른 패키
지들이 해당 패키지에 의존한 정도이고, out-degree(아웃 디그리)는 해당 패키지가 다른 
패키지에 의존하는 정도입니다. PageRank(페이지랭크)는 단순 연결 수를 넘어서 네트워
크 안에서 상대적으로 얼마나 중심적인 위치에 있는지를 보여줍니다. 또한 공유 의존성 
유사도와 코드 유사도를 활용해 대체/경쟁 후보 점수인 alt_score(알트 스코어)를 만들었
습니다. 
10쪽. 파생 변수 
파생 변수는 패키지의 의존성 복잡도, 선택 의존성 비율, 시간에 따른 의존성 변화, 코드 
내 외부 패키지 호출 밀도 등을 보기 위해 만들었습니다. 이 변수들은 단순히 연결 개수
만 보는 것이 아니라, 패키지 구조가 얼마나 복잡하고 변화하는지를 보기 위한 보조 지
표입니다. 
11쪽. 분석 방법 
분석은 크게 1차 네트워크와 2차 네트워크로 나누었습니다. 1차 네트워크는 패키지가 실
제로 다른 패키지를 직접 의존하는 관계입니다. 2차 네트워크는 두 패키지가 공통으로 
의존하는 하위 패키지가 얼마나 비슷한지를 보는 관계입니다. 이를 통해 직접 의존성 중
심성, 커뮤니티, 시간별 변화, 그리고 구조적으로 유사한 대체/경쟁 후보를 분석했습니다. 
12쪽. 5대 패키지 계열 
분석 대상 패키지는 5개 계열로 나누었습니다. LLM API(엘엘엠 에이피아이)는 openai(오
픈에이아이)나 anthropic(앤스로픽)처럼 외부 언어 모델 API(에이피아이)를 호출하는 패키
지이고, Model Runtime(모델 런타임)은 transformers(트랜스포머스)나 torch(토치)처럼 모

델을 직접 로드하고 실행하는 계열입니다. RAG/Vector DB(랙/벡터 디비)는 검색과 벡터 
저장소, Framework/Agent(프레임워크/에이전트)는 여러 도구와 모델을 연결하는 오케스

13쪽. EDA(이디에이) 1 
EDA(이디에이) 결과 먼저 전체 네트워크 규모를 확인했습니다. 2022년부터 2026년까지 
노드와 엣지가 모두 증가했고, 특히 2024년 이후 엣지 수가 크게 늘었습니다. 이는 생성
형 AI(에이아이) 패키지 생태계가 단순히 패키지 수만 늘어난 것이 아니라, 패키지 간 의
존 관계도 함께 복잡해졌다는 의미입니다. 
14쪽. EDA(이디에이) 2 
2026년 직접 의존성 구조를 보면 pydantic(파이댄틱), typing-extensions(타이핑 익스텐션
스), httpx(에이치티티피엑스), numpy(넘파이) 같은 패키지가 상위권에 나타납니다. 이들은 
생성형 AI(에이아이) 모델 자체는 아니지만, 여러 AI(에이아이) 패키지가 반복적으로 의존
하는 공통 기반 패키지입니다. 또 계열별 평균 직접 의존성 수를 보면 App/Service(앱/서
비스) 계열이 상대적으로 많은 의존성을 갖는 것을 확인할 수 있습니다. 
15쪽. 분석 결과 1 
첫 번째 분석 결과는 유명 패키지와 실제로 많이 의존되는 패키지가 다르다는 점입니다. 
왼쪽 그래프에서 openai(오픈에이아이)나 transformers(트랜스포머스)는 유명하지만, out-
degree(아웃 디그리)가 더 큰 경우가 많습니다. 즉, 다른 패키지에게 많이 의존받기보다
는 여러 기반 패키지를 가져다 쓰는 구조입니다. 반면 오른쪽 그래프에서는 pydantic(파
이댄틱), numpy(넘파이), typing-extensions(타이핑 익스텐션스), httpx(에이치티티피엑스)가 
많이 의존되는 패키지로 나타났습니다. 따라서 생태계의 얼굴은 유명 AI(에이아이) 패키
지지만, 실제 뼈대는 기반 패키지가 지탱하고 있다고 볼 수 있습니다. 
16쪽. 분석 결과 2 
핵심 네트워크를 시각화하면, 서로 다른 계열의 패키지들이 공통 기반 패키지를 중심으
로 연결되어 있습니다. 특히 회색으로 표시된 dependency(디펜던시) 노드들이 여러 
AI(에이아이) 패키지와 연결되어 있습니다. 즉 생성형 AI(에이아이) 생태계는 개별 패키지
들이 따로 존재하는 것이 아니라, 공통 의존성을 중심으로 묶인 네트워크 구조를 가집니
다. 
17쪽. 분석 결과 3 
시간별 네트워크 변화를 보면 2022년에는 비교적 단순했던 구조가 2026년으로 갈수록

티티피엑스) 같은 기반 패키지를 중심으로 여러 계열이 연결되기 시작했습니다. 이는 생

18쪽. 분석 결과 4 
다음은 중요해진 기반 패키지 분석입니다. pydantic(파이댄틱)은 2022년 in-degree(인 디
그리)가 4였지만 2026년에는 27로 증가했습니다. typing-extensions(타이핑 익스텐션스)와 
httpx(에이치티티피엑스)도 각각 4에서 23, 2에서 21로 크게 증가했습니다. 즉 과거에는 
일부 패키지에서만 사용되던 기반 패키지가 시간이 지나며 생태계 전체에서 반복적으로 
의존되는 핵심 패키지로 부상했습니다. 
19쪽. 분석 결과 5 
반대로 상대적 중심성이 낮아진 패키지도 확인했습니다. torch(토치)와 transformers(트랜
스포머스)는 여전히 중요한 패키지지만, PageRank(페이지랭크) 기준으로는 2022년에 비
해 2026년에 낮아졌습니다. 이것은 패키지의 중요성이 사라졌다는 뜻이 아니라, 생태계
가 커지면서 전체 네트워크 안에서 차지하는 상대적 비중이 낮아졌다는 의미입니다. 
20쪽. 분석 결과 6 
마지막 분석은 구조적으로 유사한 대체/경쟁 후보입니다. 상위 후보로는 anthropic(앤스
로픽)과 groq(그록), groq(그록)와 openai(오픈에이아이), google-genai(구글 젠에이아이)와 
groq(그록) 등이 나타났습니다. 이 결과는 두 패키지가 완전히 같은 기능이라는 뜻은 아
닙니다. 다만 같은 계열 안에서 공유 의존성, 네트워크 위치, 구조가 비슷하기 때문에 비
교 가능한 후보로 볼 수 있다는 의미입니다. 특히 LLM API(엘엘엠 에이피아이) 계열에서 
구조적 유사성이 높은 패키지 쌍이 많이 나타났습니다. 
21쪽. 결론 1 
결론적으로 첫째, 유명한 패키지와 실제로 많이 의존되는 패키지는 달랐습니다. 
openai(오픈에이아이), langchain(랭체인), transformers(트랜스포머스)처럼 잘 알려진 패키
지도 중요하지만, 직접 의존성 기준에서는 pydantic(파이댄틱), typing-extensions(타이핑 
익스텐션스), httpx(에이치티티피엑스), packaging(패키징) 같은 기반 패키지가 더 자주 등
장했습니다. 둘째, 2022년에는 비교적 단순했던 네트워크가 2026년으로 갈수록 노드와 
엣지가 증가하면서 여러 계열이 함께 연결되는 복잡한 구조로 확장되었습니다.
